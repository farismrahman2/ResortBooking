# Kitchen Requisition & Supplier Billing — build plan

Digitises Form "PAX KITCHEN Requisition" and the WhatsApp/cheque supplier
cycle that follows it.

## Decisions taken

| Question | Decision |
|---|---|
| Supplier access | **No logins.** The system generates one ready-to-send message per vendor, staff paste it into the existing WhatsApp groups. |
| Receipt numbers | **The supplier's own book.** Stored as reference text, never generated by us. |
| Rates | **Pre-agreed per supplier per item**, pre-fills the bill, overridable, with history. |
| Expense timing | **On delivery.** The cheque *settles* those bills; it never creates new expense rows. |

---

## The two structural problems to solve

### 1. Existing categories cannot drive the 6-vendor split

`inv_categories` has **`meat_fish` as one category**, but fish, chicken and beef
are three separate vendors. Conversely "grocery" spans four categories
(`rice_grains`, `spices`, `oil_ghee`, `packaged`). And the paper form's three
printed columns don't map to vendors either — beef, chicken, fish and eggs all
sit inside column 2 next to the vegetables.

**So the vendor is its own dimension**, tagged on the item, independent of the
existing stock category. Tag an item once, and every future requisition fans out
correctly.

### 2. Expenses would double-count

Booking an inventory receipt **already creates an expense row**
(`lib/actions/inventory.ts:372-421`) on the delivery date, with `payment_method`
hardcoded to `'cash'`.

So the cheque must **settle** existing bills, not create expenses. It also means
bills actually paid by cheque weeks later are currently recorded as cash on
delivery day — this module is the moment to correct that.

## Schema

### New: vendor dimension

```
kitchen_vendors            -- the 6 supplier slots, editable rows not an enum
  id, slug, display_name, sort_order, is_active
  seed: vegetable, grocery, fish, chicken, beef, water_drinks

inv_items      += kitchen_vendor_id   (nullable FK)  -- who supplies this item
inv_suppliers  += kitchen_vendor_id   (nullable FK)  -- which slot this supplier fills
                += is_kitchen_supplier BOOLEAN
```

### New: the requisition

```
kitchen_requisitions
  id, requisition_no        -- RQ-0008, sequential
  event_date                -- the date the food is FOR
  requisition_date
  status                    -- draft | pending_approval | approved | cancelled
  is_emergency              -- out-of-requisition order
  parent_requisition_id     -- emergency orders reference the day's requisition
  approved_by_employee_id   -- the NAMED person (mirrors sales_employee_id)
  approved_by_user_id       -- who actually clicked
  approved_at, approval_notes
  notes, created_by, created_at, updated_at

kitchen_requisition_lines
  id, requisition_id, sort_order
  item_id                   -- FK inv_items, nullable for a one-off write-in
  item_name                 -- snapshot, so renaming an item never rewrites history
  kitchen_vendor_id         -- snapshot at requisition time, same reasoning
  qty, unit_id, notes
  is_extra                  -- added after the initial draft
```

Snapshotting the name and vendor matters: re-tagging an item next month must not
silently change what last month's approved requisition said.

### Reused: the supplier bill IS an inventory receipt

`inv_movements type='receipt'` already carries supplier, `invoice_number`,
`invoice_date`, and per-line qty/rate/amount, and it already moves stock and
books the expense. Extending beats forking:

```
inv_movements += requisition_id      (nullable FK)
              += is_emergency
              += payment_status      -- unpaid | partial | paid (maintained by allocations)
```

The supplier's receipt number goes in the existing `invoice_number`.

### New: rates

```
supplier_item_rates
  id, supplier_id, item_id, rate, unit_id
  effective_from DATE, is_active
```
The bill pre-fills from the latest rate on/before the delivery date. Recording a
different rate writes a new row, so the egg price moving 11.66 → 11.34 is
visible rather than silently overwritten.

### New: the cheque

```
supplier_payments
  id, payment_no, supplier_id, payment_date
  method                    -- cheque | cash | bank_transfer
  cheque_number, bank_name, amount
  cheque_photo_path         -- private bucket, signed URLs
  notes, created_by, created_at

supplier_payment_allocations
  id, payment_id, movement_id, amount_allocated
```

One cheque covers several bills — exactly what your cheque stub records
(R-848, R-849 … totalling 93,800). The allocation table is that stub.

**Settlement, not expense:** allocating a cheque updates each covered bill's
`payment_status` and rewrites the linked expense's `payment_method` to `cheque`
with the cheque number as reference. No new expense row, so totals stay correct.

## Screens

| Route | Purpose |
|---|---|
| `/kitchen/requisitions` | List: date, requisition no, status, vendor coverage |
| `/kitchen/requisitions/new` | Create — grouped by vendor, quantities only |
| `/kitchen/requisitions/[id]` | Detail + **Approve** (named approver) |
| `/kitchen/requisitions/[id]/dispatch` | **6 WhatsApp messages**, one per vendor, copy each |
| `/kitchen/requisitions/[id]/print` | Paper form matching the current layout |
| `/kitchen/deliveries` | Record a delivery against a requisition (supplier's receipt no + rates) |
| `/kitchen/payments` | Cheque run: pick supplier → tick unpaid bills → cheque details + photo |
| `/settings/kitchen-vendors` | The 6 slots, item tagging, supplier rates |

The dispatch message reuses the existing `WhatsAppOutput` copy-to-clipboard
pattern and reproduces the format already in use:

```
Event date : 13 August 2026
Requisition : RQ 08
Receipt : —
Cow meat : 24 kg @ 700 = 16,800/-
─────────
TOTAL DUE : 16,800/-
```

## Phasing

**Phase 1 — the daily pain.** Vendors + item tagging + requisition + approval +
WhatsApp dispatch + print. This alone replaces the paper form.

**Phase 2 — money in.** Deliveries linked to requisitions, supplier rates,
emergency orders.

**Phase 3 — money out.** Cheque runs, allocation against bills, cheque photo,
and the `payment_method` correction on inventory expenses.

Deliberately staged so Phase 1 is usable in the kitchen before Phase 2 exists —
one long build with nothing testable until the end is the failure mode here.

---

## Open items, deliberately deferred

- **Bangla item names.** The paper form is entirely in Bangla. `inv_items.name`
  is free text so it already holds Bangla, and Noto Sans Bengali is already
  loaded. Whether staff want Bangla-only, English-only, or both side by side is
  a call to make once they see Phase 1.
- **Who may approve.** `employees` has no approver flag. Simplest is to allow any
  employee with `inventory:write`, recording the named person. A dedicated
  `is_approver` flag can come later if the list needs narrowing.
- **Multiple suppliers per vendor slot.** Modelled as many-suppliers-to-one-slot
  with a default, so a second beef supplier doesn't require a migration.
